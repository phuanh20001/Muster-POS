### Added
- **LAN TLS is installed, running and chain-verified, the static IP is set, and the certificate deliberately covers a hostname as well as the IP so the tablets survive the address changing.** With the iPads not at home, the expensive mistake to design out was **picking the wrong IP**: a cert issued only for an address is *pinned* to it, so a clash with the shop's DHCP pool would mean a certificate error on every tablet and a lap of the shop re-trusting each one by hand. The [Caddyfile](Caddyfile) now serves **two site addresses** — `{$POS_LAN_HOST}` and `{$POS_LAN_NAME:dreamy-cafe.local}` — and [install-caddy-service.ps1](scripts/install-caddy-service.ps1) gained a `-LanName` parameter defaulting to this box's own name plus `.local`, passed through to the service environment. Caddy issues a **separate cert per name** (`192.168.0.10.crt` with `IP Address=192.168.0.10`, `dreamy-cafe.local.crt` with `DNS Name=dreamy-cafe.local`) from the **same** `Caddy Local Authority - ECC Intermediate`, so one root trust on the iPad still covers both. Net effect: an address change becomes one command instead of a tablet-by-tablet re-trust, which is why the tablets should be bookmarked to the **name** and the IP kept as the fallback — the reverse of the usual advice, and correct here because the IP is the thing most likely to move. **Static IP set to `192.168.0.10/24`**, gateway and DNS `192.168.0.1`, on **`Ethernet 2`** (the adapter the shop will actually use, not the Wi-Fi dongle). `.10` chosen because low addresses sit below most consumer DHCP pools, `.12` and `.4` are the printers, and nothing observed on the LAN (`.1 .22 .88 .101 .195 .230`) uses it; the script **pings the target first** and aborts rather than claim an address something else holds. ⚠ Two things checked before touching the network, because both would have been ugly: the DHCP lease was only **2 hours** (22:03 → 00:03), confirming the old `.22` really would have drifted; and `qwinsta` showed an **active RDP session** — but it rides the **Tailscale** interface (`100.x.x.x`), not `Ethernet 2`, so changing the LAN address could not drop it. `DREAMY-CAFE.local` re-resolved to `.10` immediately afterwards, which is what makes the hostname approach viable at all. Caddy is registered as `DreamyCafeCaddy` (auto-start, depends on `DreamyCafeApp`), firewall now **allows 443/80 and BLOCKS 3000**, and both names return **200 on `/api/health` with the chain verified**. 🟠 Still unverified and deliberately not claimed: whether the shop's router passes **mDNS** — if it blocks Bonjour, `.local` will not resolve there and the tablets fall back to the IP. - **The mini-PC was profiled for longevity, and the measurement overturned the premise: SSD wear is a non-issue by three orders of magnitude, so most of what an "optimise Windows for SSD life" pass would have changed was deliberately left alone.** The codebase has had a lot of attention and the host OS none, so the box was measured before anything was touched. `Get-StorageReliabilityCounter` reports the Toshiba KXG6AZNV256G at **`Wear: 0`, 27 °C, HealthStatus Healthy**. Write attribution was done through `Win32_Process.WriteTransferCount ÷ process age` — CIM rather than `Get-Process`, for the same reason [verify-resilience.ps1](scripts/verify-resilience.ps1) uses CIM: it needs no process handle and so reads SYSTEM-owned processes unelevated. **The first result was misleading and is worth recording as a method note.** Whole-machine write rate came to **1,319 MB/h → 11 TB/year**, which looks alarming until you read the ranking: `Code.exe` 837 MB/h, `chrome.exe` 51, `claude.exe` 13 — the top writers are *this workstation session*, none of which exists on a headless POS. Re-measuring only the production processes (`node.exe`, `postgres.exe`, `GoogleDriveFS.exe`, `nssm.exe`) gives **3.11 MB/h → 0.073 GB/day → 0.026 TB/year**, or **~3,800 years** against a conservative 100 TBW rating. Turning either off benchmarks dramatically faster and trades away the last committed transactions — or a torn page — on power loss. This box has **no UPS by design** and takes card payments, so a charged customer whose order vanished is not a performance trade available to us. Both were re-read and confirmed `on` after the one change that *was* made. **Two of my own suspicions were killed by evidence rather than confirmed**, which is the reason to measure first: the Security event log looked like it was churning at 26 MB/h, but it holds **827 hours — 34 days — of history in 20 MB**, so that rate was transient (today's reboot, Windows Update, and the auditing itself); and the `svchost` writing 133 MB/h turned out not to be telemetry or indexing but **`DoSvc`**, which is a genuine finding in its own right (below).

### Fixed
- **Delivery Optimization was the single largest disk writer on the machine and was set, by Windows default, to upload update content to strangers over the shop's internet connection — the same link that carries Square card authorisations.** Neither `HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\DeliveryOptimization` nor its Policies key existed, and absent a policy the default download mode is **peer-to-peer (HTTP + LAN + internet peering)**. Measured at **132.7 MB/h**, `DoSvc` out-wrote every other process on the box — including the POS itself — by a factor of ~40. **The reason to change it is bandwidth, not wear:** 133 MB/h is still only ~1.1 TB/year against a 100 TBW drive, so this is not a longevity fix; it is that an upload burst during service competes with a card authorisation, and a payment that spins is the expensive failure. Now set in [configure-windows-updates.ps1](scripts/configure-windows-updates.ps1) as a new section 5: **`DODownloadMode = 0`** (Delivery Optimization's download manager is kept for its resume and throttling behaviour, but peering is off entirely — HTTP from Microsoft only, nothing shared outward) and **`DOPercentageMaxBackgroundBandwidth = 40`**, exposed as `-MaxUpdateBandwidthPercent` with an `-AllowUpdatePeering` escape hatch for a shop that deliberately wants the default. The cap applies to **background** traffic only, so a manually-triggered update still runs at full speed when someone is deliberately waiting for it. **Applied and verified:** `DoSvc` restarted and now reports **1.25 MB/h**, and free space went from **198.3 GB to 200.8 GB**. ⚠ **Honest attribution: the 133 → 1.25 drop is not all policy.** The original figure was sampled while today's Windows Update work was actually running, so part of the fall is simply that nothing is downloading now. The policy is correct on its own terms — no outward sharing, capped background use — and should not be credited with the whole delta.
- **The monthly maintenance job now tracks SSD *temperature*, which on this hardware is the metric that matters, and prunes the Windows temp folders, which nothing else does.** [db-maintenance.ps1](scripts/db-maintenance.ps1) already read `Wear`, `PowerOnHours` and uncorrected error counts, but **not `Temperature`** — and the write profiling above inverts which of those deserves attention. Wear is a ~3,800-year problem; heat is a real one, because this is a Mini/DM chassis with a single small blower fan destined for a café, where grease and flour clog an intake in a way an office never does, and heat is what kills NVMe controllers and nearby capacitors. Temperature now appears in every log line (`temp=27C` on the first run) with a two-tier response matching the existing wear tiers: **60 °C logs a "check the fan and vents" warning**, **70 °C raises the same alarm as a failing drive** (these drives throttle around 70–80 °C). The threshold matters less than the direction, which is why the reading goes to `logs\db-maintenance.log` every run — a slow climb over a year is the actual signal, and it is invisible unless each reading is kept. **Second addition: temp-folder pruning.** Storage Sense is off by default on Pro and nothing else clears these, so by **day two** of this build there was **933 MB in `C:\Windows\Temp` and 911 MB in the user's Temp** — 1.8 GB of creep. Disk creep is the mechanism that eventually trips `backup-db.ps1`'s 5 GB free-space alarm, which is the one failure that stops PostgreSQL writing and therefore **stops sales**. The prune only touches files older than 7 days so a running installer's scratch files are never pulled out from under it, and every delete is swallowed per-file because a locked temp file is normal and must not fail the run. **First real run freed 775.9 MB.** ⚠ **One behaviour was found during that run and made explicit rather than left as a trap:** `C:\Windows\Temp` reported *"removed 0 file(s), 0 in use"* against a folder holding 933 MB — because most of it is SYSTEM-owned and an unelevated shell cannot even **enumerate** it, so `-ErrorAction SilentlyContinue` swallowed the failure at the listing stage and the pass looked clean rather than blocked. The scheduled task runs `RunLevel=Highest` and does clear it; a manual run from a normal window will not. The script now detects elevation and logs exactly that, so nobody reads a silent zero as a broken prune.
- **PostgreSQL's `random_page_cost` was still `4` — a spinning-disk assumption on an NVMe box.** The default encodes "a random read costs 4× a sequential one because the head must seek", which is false on flash; left at 4 the planner over-prices random I/O and prefers sequential scans where an index scan would win. Now **`1.1`**, the standard SSD value, applied with `ALTER SYSTEM` + `pg_reload_conf()` and confirmed `pending_restart=false` — **no database restart and no outage.** On a 10 MB database this changes nothing measurable today; it is worth doing now because it silently starts mattering as the orders table grows, which is exactly the kind of thing nobody revisits. 🟠 **`shared_buffers` was deliberately left at its 128 MB default**, against the usual "25% of RAM" advice: the whole database is **10 MB**, so it already fits many times over, and raising it would require a PostgreSQL restart to buy nothing. Recorded as a revisit-when-the-database-passes-~500 MB item instead — at roughly 200 orders/day that is several years out.

ON CONFLICT DO UPDATE .. RETURNING` — the `ON CONFLICT` takes a row lock, so a second till waits for the first to commit rather than reading a stale value the way `SELECT max(dailyNumber) + 1` would; two tablets ringing simultaneously is the *normal* case here, not an edge case. Online orders draw it in `fulfillPaidOrder` **at payment, not at checkout creation**: online orders are created `AWAITING_PAYMENT` and abandoned checkouts are swept, so numbering at creation would have riddled the day with holes for orders that never existed, and it also correctly dates a ticket by the day it is *made* rather than the day someone opened a payment page. Numbering there is also **non-fatal by design** (logged, never thrown): it runs after the exactly-once status-flip claim, and a DB hiccup must not cost the customer their loyalty stamps or leave a paid order sitting unprinted when the fallback is simply a docket headed by its id. **The timezone trap is the part most likely to be reintroduced.** `createdAt` is stored in UTC, so grouping orders into trading days with `createdAt::date` files every order rung after 10am AEST under the *next* day — which is why day keys are computed in JS via `localDayKey` and why [backfill-daily-numbers.js](prisma/backfill-daily-numbers.js) is a Node script rather than one clever `UPDATE`. The backfill is optional (old orders already fall back to their id), re-runnable, resumes each day from its counter, and skips `AWAITING_PAYMENT` rows. Test rows deleted, `OrderDayCounter` left empty. The migration is applied (`20260730000000_add_daily_order_numbers` — both columns nullable, unique index `Order_businessDate_dailyNumber_key` present), which is safe to do ahead of the code because it is purely additive and the running build simply ignores columns it does not know about. **Deployed and live**: service stopped → `prisma generate` → `npm run build` → service started → `/pos` returns **200**. The stop is not optional and is now recorded in [AGENTS.md](AGENTS.md): `prisma generate` fails `EPERM: … rename query_engine-windows.dll.node` while `DreamyCafeApp` holds the engine DLL, because Windows will not let a mapped image be replaced — and **killing Node is not enough, since NSSM restarts it**. 🟠 Worth flagging as a latent trap in the deploy path itself: [deploy.ps1](scripts/deploy.ps1) builds at step 4 **while the service is still running** (deliberately, so a failed build never restarts the app), which means `npm run build` inside it will hit this same EPERM on *any* schema change.
